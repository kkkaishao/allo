## Layer 1: type system

1. `buffer` types: `!act.scalar<i32>`, `!act.vector<4xf32>`, `!act.tile<4x4xf32>`. These buffer types represent how the scratchpad is accessed (its granularity). For example, `!act.vector<4xf32>` means that the scratchpad is accessed in 4-element vector granularity, and each element is a 32-bit float. All the `buffer` types are inherited from a common `BufferTypeInterface`
2. `desc` types: `!act.desc<["offset":i32, "stride":i32]>`, `!act.desc<["base":i32]>`. These descriptor types represent the fields of a descriptor. For example in a TMA descriptor, we may have an "offset" field and a "stride" field, so we can define a descriptor type `!act.desc<["offset":i32, "stride":i32]>`.
3. `state` types: `!act.state<i32>`. The primitive type (`i32` in this case, and must be int types) represents the hardware primitive type of the state.

## Layer 2: type related operations

1. `buffer` operations
  1. `act.buffer @name size=8 : !act.vector<4xf32>`: declare a buffer with the given name, size and type. The size is in `buffer` elements, so in this case the buffer has 8 elements of type `!act.vector<4xf32>`. Size must be an int attribute, since no actual hardware supports multidimensional buffers more than 2D.
2. `desc` operations
  1. `act.desc @name size=8 : !act.desc<["offset":i8, "stride":i8]>`: declare a descriptor with the given name, size and type. The size represents the number of descriptor slots, and each slot can hold one descriptor of the given type. So in this case the descriptor has 8 slots, and each slot can hold a descriptor with "offset" and "stride" fields.
  2. `act.desc.write %value to "field" in @desc : i8`: write a value to a field in a descriptor. The value must be of the same type as the field in the descriptor type. For example, if the descriptor type is `!act.desc<["offset":i8, "stride":i8]>`, then the value must be an `i8`.
  3. `%value = act.desc.read "field" from @desc : i8`: read a value from a field in a descriptor. The value must be of the same type as the field in the descriptor type.
3. `state` operations
  1. `act.state @name enums = ["os", "ws"]: !act.state<i32>`: declare a state with the given name, enums and type. The enums represent the possible values of the state, and the type represents the hardware primitive type of the state. The actual values of the enums are implicited generated by the order in the enum list.
  2. `act.state.write "os" to @state : i32`: write a value to a state. The value must be one of the enums defined in the state declaration, and must be of the same type as the state type.
  3. `%value = act.state.read @state : i32`: read a value from a state. The value must be of the same type as the state type.
  4. Note: conditional writing to state achieve by `scf.if %cond { act.state.write "os" to @state : i32 } else { act.state.write "ws" to @state : i32 }`. We explicitly reject `act.state.write %value to @state : i32` where the value is arbitrary, because we want to make sure the state is only written with valid values.
  5. Dynamic execution path selection can be achieved by `%0 = act.state.read @name : i32, arith.cmpi "eq" %0, %c0 : i32`, where `%c0` is a constant representing one of the enums defined in the state declaration.

## Layer 3: Memory access operations (Memory Access Pattern as First-Class Citizens)

1. `act.strided base(%0) counts(%1, 0) strides(%2, 1)`: define a strided access pattern. Its base, counts, strides can be a mixture of static and dynamic values (like `tensor.extract_slice`). The number of counts and strides must be the same
2. `act.tiled base(%0) counts(%1, 0) strides(%2, 1) tile_sizes(%3, 4)`: define a tiled access pattern. Its base, counts, strides, tile_sizes can be a mixture of static and dynamic values. The number of counts, strides and tile_sizes must be the same.
3. Contiguous access pattern is treated as a special case of strided access pattern
4. All the access pattern operations inherits from a `BufferAccessPatternOpInterface`, which requires them to implement several methods:
  1. `verifyCompatibility(BufferTypeInterface buffer, std::size_t size)`: check if the access pattern is possibly compatible with the given buffer type and size.
  2. `materialize(OpBuilder&, Location, Value buffer, bool enableTensor)`: materialize the access pattern into actual IR code that access the given buffer (e.g. `tensor.extract_slice`/`memref.subview`), and return the accessed value.
  3. `materialize(OpBuilder&, Location, Value value, Value buffer)`: materialize the access pattern into actual IR code that write the given value to the given buffer (e.g. `tensor.insert_slice`).
5. All the operations return a NoneType SSA value as a token representing the access pattern

## Layer 4: Instruction operations

```mlir
act.define @demo {
  src(@spad, @spad) dst(@spad)
  addr(%arg0: index, %arg1: index) {
    %0 = act.strided base(0) counts(%arg0) strides(4)
    %1 = act.tiled base(0) counts(12) strides(%arg1) tile_sizes(1)
    act.yield %0, %1, %1
  }
  compute(%0: tensor<12x12xf32>, %1: tensor<12x12xf32>, %2: tensor<12x12xf32>, %extra: index) {
    // ...
    act.yield %some_value
  }
}
```
define an instruction with a name, source and destination memory spaces, address parameters, access patterns, compute parameters, and semantics. The source and destination memory spaces must be defined by `act.buffer` operation. The `addr` region defines the access patterns for every source/destination, thus must yield the same number of access patterns as the number of sources/destinations. The address parameters are the block arguments of the address region, and are used to define dynamic access patterns (must be index type). The `compute` region defines the actual computation semantics of the instruction — its first N block arguments correspond to the N source+destination buffers (must be ranked tensors), and any additional block arguments are compute parameters (must be int or index types) that can be used for dynamic computation. The semantics region only represents how the computation is related to the inputs/outputs, so its buffer block arguments don't need to have the same extents as where the instruction is invoked. However, the ranks and element types must match the accessed buffer types (enforced by the verifier). The semantics region must yield the same number of values as the number of destination buffers.
In one word, the compute region is a template for the actual computation that will be inlined at the emit site, and the address region defines how to access the buffers at the emit site.

The compute region must only use limited set of operations to compose the instruction semantics. Supported operations are:
1. `arith.*` operations, with operands limited to scalar values (0-d tensors are not supported)
2. Some of commonly used `math.*` operations
3. `tensor.extract_slice`, `tensor.insert_slice`, `tensor.collapse_shape`, `tensor.expand_shape`
4. `linalg.generic`, `linalg.yield`, `linalg.map`, `linalg.reduce`, `linalg.transpose`, `linalg.fill`, `linalg.contract` (All supported via `Reify` interface);

```mlir
act.emit @demo addr(%0, 12) compute(%1)
```
emit an instruction defined by `act.define`. The `addr` parameters correspond to the address region block arguments and control buffer access patterns. The `compute` parameters correspond to the extra (non-buffer) block arguments of the compute region. Both can be a mixture of static attributes and dynamic SSA values (index type for dynamic). During lowering, the compute region of the instruction will be inlined at the emit site, with the address params mapped to the given values to materialize access patterns, and the compute params mapped to the extra block arguments of the compute region. The buffer block arguments of the compute region will be replaced by the inferred types from the accessed buffers.


## Layer X: Conversion pass
Since the instruction semantics is defined with upstream MLIR operations, it's not hard to convert the instruction into actual MLIR code by instantiating the access and semantics regions at the emit site in a structural way.

Typically, the pass works as follows:
1. For each `act.buffer`, allocate a global buffer with `memref.global`
2. For each `func.func`, create `memref.get_global` for every `act.buffer` instances at the beginning of the function
3. For each `act.emit`, clone the address region with `addr` params mapped, then call `materialize` method on each access pattern op to generate actual buffer access code. After that, inline the compute region, with buffer block arguments replaced by the materialized slices and compute block arguments replaced by the `compute` params.
4. After inlining, generate code with `materialize` method to write the results yielded by yield in the compute region back to the destination buffers. Note, if the buffer is memref typed, then no need to materialize the access pattern again, since memref values are always in-place updated.
5. Finally cleanup all the `act` operations (e.g. access patterns, instruction definitions, etc)

The most important part of the pass is how to instantiate the compute region. The basic idea is leveraging `inferReturnTypes` or `ReifyRankedShapedTypeOpInterface` to infer the actual types for LinalgStructuredOps. For `arith.*` operations, it's quite trivial to infer the result type from the new operand types.

The implementation is placed in `mlir/lib/act/Conversion/ConvertActToCanonicalForm.cpp`, and only the `enableTensor` path is supported preliminarily. The path with `enableTensor=false` is not working currently (supporting it is low priority).

## Layer X+1: Lower to LLVM for simulation
Lowering to LLVM is straightforward, through a predefined lowering pipeline.

The pipeline is defined in `mlir/act/lib/Conversion/LowerToLLVM.cpp`. After the lowering, we may use `mlir-translate -mlir-to-llvmir` to emit LLVM IR, and compile it with `clang` for CPU simulation. So the pipeline doesn't include optimizations like loop-tiling, vectorization, etc, and we use clang's optimization passes for that.

Also it is possible to simulate with GPUs, since there are lots of third-party MLIR-based GPU codegen backends that consume standard MLIR operations. The feature may be supported in the future.

## Design Note: Sub-element operand modes (broadcast, shuffle, etc.)

Some SIMD instructions operate at sub-element granularity — e.g., selecting a single lane from a vector register and broadcasting it to all lanes before computation. The current access pattern abstraction (`act.strided`, `act.tiled`) operates at buffer-slot granularity, so it cannot express these modes.

The preferred direction is to extend the access pattern layer (Path B) — e.g., an `act.broadcast` op that wraps a buffer access and describes the sub-element transform. This keeps the compute region purely about computation, which matters for instruction selection: `vmul` and `vmul_broadcast` share the same compute (`linalg.mul`) and differ only in how a source operand is fetched. Factoring operand modes into addr avoids N×M pattern explosion (N operand modes × M compute ops) and keeps subgraph matching clean.

An alternative (Path C) is a separate "transform" region between addr and compute, but this adds structural complexity and is likely premature until more operand mode patterns are known.

This is not implemented in the current instruction selection path. It should be revisited only when concrete operand-mode workloads require it.

## Design Decision: Separation of Computation and Access Regions

### Motivation

The original `act.define` design allows the compute region to contain layout transforms (e.g., `tensor.expand_shape`, `tensor.collapse_shape`) that bridge between a buffer's flat storage layout and the shapes that computation ops require. For example, `@matmul` in `tpu.mlir` stores data in a 1D buffer (`tensor<16xf32>`) but needs 2D tensors for `linalg.matmul`, so the compute region contains `expand_shape` before the matmul and `collapse_shape` after it.

This conflation creates three problems:

1. **Instruction selection requires heuristic boundary stripping.** To determine *what computation* an instruction performs, the selector must identify which layout ops are "boundary transforms" (bridging buffer layout to compute shape) versus "interior transforms" (part of the computation itself, like transpose-then-matmul). Stage 1 implemented this via fixed-point iteration (tracing SSA flow from block args and yield), but it is fundamentally a heuristic — it infers a distinction that should be explicit in the IR.

2. **Semantic fingerprints are polluted by access concerns.** The fingerprint of `@matmul` should be `linalg.matmul`, but with boundary transforms in the compute region, the extractor must first strip them. If the stripping heuristic is wrong (e.g., an instruction with a *semantic* reshape that happens to sit at the boundary), the fingerprint is wrong and matching fails silently.

3. **Symbolic shape solving becomes ill-defined.** For Stage 2 (tiling and address parameter generation), we need to determine an instruction's "native computation shape" — the tensor shapes it operates on per invocation. When boundary transforms live in compute, the native shape depends on both the compute region (which contains the reshapes) and the addr region (which controls buffer access), with complex coupling through shared parameters like `%size`. Separating them makes the native shape directly readable from the compute region's block argument types.

### The Separation Principle

**Compute regions must contain only computation.** All shape adaptation between buffer storage layout and compute-native tensor shapes belongs in the addr region, expressed as relayout ops on access pattern tokens.

After separation:
- **Compute region block arguments directly reflect the shapes the computation operates on.** A matmul instruction's compute region takes `tensor<?x?xf32>` operands — the shapes the hardware's multiply-accumulate unit sees.
- **Addr region handles all layout mapping.** Base access patterns (`act.strided`, `act.tiled`) describe how to address buffer slots. Relayout ops (`act.expand_shape`, `act.collapse_shape`, `act.transpose`) transform the accessed data's shape before it reaches the compute region.
- **The yielded access pattern token carries both addressing and shape information.** During lowering, materializing a token produces the buffer slice *and* any reshaping needed.

### Effects on each pipeline component

| Component | Before (mixed) | After (separated) |
|-----------|----------------|-------------------|
| Stage 1 (semantic matching) | Needs boundary stripping heuristic to extract fingerprint | Fingerprint is directly the compute region's core ops. Boundary stripping repurposed as a validator — warns if layout ops are found in compute (indicates ISA author error) |
| Stage 2 (tiling) | Native shape requires analyzing compute region + addr region jointly | Native shape = compute region block arg types |
| Conversion pass (`ActToCanonicalForm`) | Inlines compute region with boundary transforms already present | Materializes addr relayout ops into `tensor.expand_shape` etc., then inlines pure compute |
| Verifier | Must check consistency between buffer types and compute block args with transforms in between | Direct type compatibility check: addr output shape must match compute block arg shape |
| ISA authors | Mix access and compute concerns in one region | Clear separation — addr describes "how to fetch/store", compute describes "what to compute" |

### Concrete example

Before:
```mlir
act.define @matmul {
  src(@devmem, @devmem) dst(@devmem)
  addr(%addr_a: index, %addr_b: index, %addr_c: index, %size: index) {
      %cnt = arith.muli %size, %size : index
      %0 = act.strided basis(%addr_a) counts(%cnt) strides(1)
      %1 = act.strided basis(%addr_b) counts(%cnt) strides(1)
      %2 = act.strided basis(%addr_c) counts(%cnt) strides(1)
      act.yield %0, %1, %2 : none, none, none
  }
  compute(%a: tensor<16xf32>, %b: tensor<16xf32>, %c: tensor<16xf32>, %size: index) {
      %0 = tensor.expand_shape %a [[0, 1]] output_shape [%size, %size]
      %1 = tensor.expand_shape %b [[0, 1]] output_shape [%size, %size]
      %2 = tensor.expand_shape %c [[0, 1]] output_shape [%size, %size]
      %3 = linalg.matmul ins(%0, %1) outs(%2) -> tensor<4x4xf32>
      %4 = tensor.collapse_shape %3 [[0, 1]]
      act.yield %4
  }
}
```

After:
```mlir
act.define @matmul {
  src(@devmem, @devmem) dst(@devmem)
  addr(%addr_a: index, %addr_b: index, %addr_c: index, %size: index) {
      %cnt = arith.muli %size, %size : index
      %0 = act.strided basis(%addr_a) counts(%cnt) strides(1)
      %0r = act.expand_shape %0 [[0, 1]] output_shape [%size, %size]
      %1 = act.strided basis(%addr_b) counts(%cnt) strides(1)
      %1r = act.expand_shape %1 [[0, 1]] output_shape [%size, %size]
      %2 = act.strided basis(%addr_c) counts(%cnt) strides(1)
      %2r = act.expand_shape %2 [[0, 1]] output_shape [%size, %size]
      act.yield %0r, %1r, %2r : none, none, none
  }
  compute(%a: tensor<?x?xf32>, %b: tensor<?x?xf32>, %c: tensor<?x?xf32>) {
      %0 = linalg.matmul ins(%a, %b) outs(%c) -> tensor<?x?xf32>
      act.yield %0
  }
}
```

The compute region is now purely `linalg.matmul`. The addr region encodes the full access-and-reshape pipeline.

## Instruction Selection Implementation Overview

> Current implementation details are split across [stage1.md](stage1.md),
> [stage2.md](stage2.md), and [stage3.md](stage3.md). This section is the
> top-level map of the implemented pipeline in `mlir/lib/act/Support`.

### Goal and scope

The instruction selection pass lowers a flat tensor-level `func.func` into an
`act.sequence` containing concrete `act.emit` instructions. It is implemented by
`ConvertCanonicalFormToAct.cpp`, with the stage-specific logic factored into:

- `SemanticMatching.cpp`: build source and instruction semantic graphs, then
  select a complete instruction covering.
- `SymbolicExpr.cpp` and `ParamSolving.cpp`: derive symbolic access models from
  instruction addr regions and solve shape-controlled addr parameters.
- `Planning.cpp`: build an execution plan, allocate HBM/scratch resources, insert
  data movement, and produce a flat schedule.
- `CodeEmission.cpp`: emit the scheduled `act.emit` ops into a new
  `act.sequence`.

Current backend contract:

- The input function must have exactly one block, no control flow, and no symbol
  users. The pass rejects `LoopLikeOpInterface`, branch, and region-branch ops.
- Tensor boundary shapes must be ranked and static.
- The backend does not tile and does not generate loops. Inputs must already be
  shaped so every selected instruction invocation fits exactly.
- Addr params are emitted as static integer attributes. Dynamic offsets and extra
  compute params are not implemented in the current code emission path.
- `act.tiled` symbolic shape/storage extraction is not supported in the current
  implementation.

### Pass pipeline

The pass invoked by `-convert-canonical-form-to-act` runs as follows:

1. Optionally parse and inline an external ISA module when `isa-path` is set.
2. Normalize the input module with `linalg-morph-ops` (`genericToNamed`),
   `canonicalize`, and `cse`.
3. Build an `InstructionCollection` from all non-identity `act.define`
   instructions in the module. Identity instructions are ignored by semantic
   matching and are used later as data movement candidates.
4. For each `func.func`, validate the flat-function contract.
5. Run Stage 1 to build a `SemanticGraph`: source semantic ops are covered by
   selected instruction graphs, and boundary values are bound to instruction
   access operands.
6. Run Stage 2 to build an `InstructionParamModel` for each selected
   instruction and solve shape parameters from the matched source tensor shapes.
7. Run Stage 3 planning to assign HBM regions, scratch placements, forwarding,
   load/store moves, and a final schedule.
8. Emit a new `act.sequence @func_name` and erase the original `func.func`.

### Stage 1: semantic matching

Stage 1 treats computation and layout separately. Primitive semantic ops become
graph nodes. Layout and placeholder ops are not selected directly; they are
traced as `LayoutChain` metadata on graph edges so later stages know which
source boundary value and static slice feed an instruction operand.

The current primitive semantic set is:

- `linalg.generic`, `linalg.softmax`, `linalg.map`, `linalg.reduce`,
  `linalg.contract`
- `linalg.add`, `linalg.matmul`

An `InstructionGraph` is built from each instruction compute region using the
same node/edge representation as the source `ProgramGraph`. Matching uses an
anchor node selected by graph degree, a hash-based lookup on the anchor semantic
identity, and backtracking subgraph matching with induced-exact internal edges.
The selected candidates must cover every primitive source semantic op; partial
lowering is rejected.

### Stage 2: parameter solving

Stage 2 is exact shape fitting, not tiling. For each selected instruction, the
addr region is converted into symbolic access models:

- `visibleShape`: what the compute region sees for each source/destination
  operand.
- `storage`: the underlying strided basis/count/stride region used for resource
  planning.
- `paramKinds`: addr block arguments classified as `Shape`, `Offset`, or
  `Mixed`.

Symbolic expressions support constants, addr params, `arith.addi`, and
`arith.muli`. `act.strided`, `act.expand_shape`, `act.collapse_shape`, and
`act.transpose` have shape semantics; relayout ops preserve the underlying
storage region for allocation. Every access operand must receive a static source
shape constraint from Stage 1 bindings. Constants must match exactly; params are
bound to the concrete source dimension; simple add/mul expressions can be solved
when one side is already known. Inconsistent or unsupported constraints reject
the match.

### Stage 3: planning and code emission

Stage 3 converts the semantic graph plus parameter solutions into concrete
emission:

1. Create `PlanNode`s and logical values from selected semantic nodes.
2. Allocate one flat HBM address space for tensor function args/results using the
   single declared `!act.hbm` buffer.
3. Allocate non-HBM scratch resources for instruction operands. Current scratch
   allocation supports one-dimensional, unit-stride on-chip storage regions.
4. Track lifetimes and reuse placements when safe. Producer-to-consumer scratch
   forwarding is detected before inserting data movement.
5. Build a data movement catalog from identity `act.define` ops with one source
   and one destination. Layout signatures currently record transposes.
6. Insert required load, scratch-to-scratch, store, or one-hop store moves around
   compute actions.
7. Emit a flat `act.sequence` schedule. Each schedule step becomes one
   `act.emit @instruction addr(...) compute()` with static dense integer attrs.

### Current limitations and possible extensions

These are unsupported by the current implementation. They are not committed
roadmap items; each one should be evaluated only if a concrete workload needs it.

- Region-local lowering inside loop bodies, control-flow-aware selection, or
  dynamic affine offset emission.
- Backend tiling or padding. The current design keeps tiling/padding outside the
  backend: the input should already be shaped for exact instruction fits.
- Extra compute params and dynamic addr SSA operands in `act.emit`.
- More complete primitive semantic op coverage and transform-chain comparison
  during graph matching.
- Diagnostics that report all failed candidate reasons instead of failing at the
  first unsupported shape, layout, or movement case.
